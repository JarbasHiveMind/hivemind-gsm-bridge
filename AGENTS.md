# AGENTS.md — `hivemind-gsm-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a physical GSM/USB modem's SMS to a HiveMind node: a HiveMind bridge is
a satellite whose input and output are a chat platform instead of a microphone.
Inbound SMS received by the modem become `recognizer_loop:utterance` bus
messages; the hub's `speak` replies are sent back as SMS to the original
sender. It needs real hardware (a GSM/USB modem and an SMS-capable SIM) and has
only been exercised with both the modem and the HiveMind client mocked — never
against a live modem or a real hub. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape:
[hivemind-telegram-bridge](https://github.com/JarbasHiveMind/hivemind-telegram-bridge)
and the other chat-platform bridges under the org — check them for prior art
before inventing a new pattern here.

## Layout / build / test

- Package module: `hivemind_gsm_bridge/`. Tests live in `tests/` (check before
  adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks both
  `gsmmodem.modem.GsmModem` and `HiveMessageBusClient`, so it runs without a
  physical modem or a live hub — that also means it cannot catch a real serial
  failure, a real handshake hang, or a real network SMS delivery break; treat
  it as a shape/wiring check, not a live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindGSMBridge` builds (or accepts an
  injected) `HiveMessageBusClient` in `__init__` but does **not** connect it
  there — `HiveMessageBusClient.__init__` never opens a socket. The actual
  connection happens once, in `connect_hivemind()`, called from `start()`.
  Never add a second call to `connect()` or `run_forever()` — the client
  already owns and runs its own reconnect worker thread once `connect()`
  returns. The GSM modem follows the same pattern: `modem` is built lazily via
  the `modem` property (or injected for tests) and only actually opened by
  `modem.connect(sim_pin)` in `start()`.
- **`connect()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever. `connect_hivemind()`
  currently calls `self.client.connect(site_id=self.site_id)` with no explicit
  bound, so it hangs indefinitely against a stalled or unreachable hub instead
  of failing fast — this is a standing requirement, not yet met: any change
  touching `connect_hivemind()` must add an explicit finite
  `handshake_max_retries`, exposed as a constructor parameter so operators can
  tune it.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`) on the hub. This
  bridge has no way to grant itself permissions and must not try to work
  around a denial locally — a silently dropped message on the hub side is the
  hub doing its job, not a bug here.
- **Rejected credentials must fail fast.** A bounded `handshake_max_retries` is
  what turns "wrong access key/password" into a clean failure instead of a
  bridge that spins forever looking connected. Do not add retry/backoff logic
  on top of `connect()` that defeats this.
- **Return upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to SMS unmodified; do not reformat, truncate, or
  add bridge-specific decoration to hub-authored text. The one exception is the
  fixed fallback line on `hive.complete_intent_failure`, which is
  bridge-authored by design because the hub sent no utterance to relay.
- **Drop SMS received before the handshake completes.** `handle_incoming_sms()`
  checks `self._connected` and drops anything received before
  `connect_hivemind()` finishes — forwarding earlier would hit an unconnected
  client instead of just failing the one message. Keep this guard if you touch
  the incoming-SMS path.
- **Thread safety.** `handle_speak()` and `handle_intent_failure()` run on the
  HiveMind bus's own worker thread, not on any modem-owned thread; `sendSms()`
  is a blocking serial call. There is no asyncio loop in this bridge (unlike
  the async-client bridges), so no `run_coroutine_threadsafe` bridging is
  needed here — do not add one without a concrete reason.
